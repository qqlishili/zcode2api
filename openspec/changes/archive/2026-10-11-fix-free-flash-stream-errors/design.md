# Design

## Context

问题见 `proposal.md`。三条流共用 `_Upstream`，但分别消费 bytes/lines；账号最近结果目前在收到响应头时提前写成功。Responses 已有 `fail()`，连接和槽位已有幂等 `close()`。

## Goals / Non-Goals

**Goals:** 在现有网关层识别错误并收口三协议、监控和账号结果。

**Non-Goals:** 不改纯转换器接口、选号算法、账号健康分类、免费额度领取、订阅能力或 VPS 发布方式；本次不把无错误事件的截断流扩展成新协议校验任务。

## Decisions

1. 网关共用一个小型流错误检查，识别 `type: error` 并使用固定失败说明。Chat 输出错误 JSON 后结束；Responses 复用 `fail()`；Messages 在现有行缓冲旁路识别，保持原始字节透传。相比在两个转换器各造异常，网关层能同时覆盖直通协议。
2. 失败监控及账号结果在产出错误终态前记录，避免终态 yield 时取消覆盖结论。已提交响应头保持 HTTP 200，监控 `status` 记录实际 HTTP 200、`ok=false` 表示业务失败，不虚构客户端收到 502。
3. `_Upstream` 仅增加可选、一次性的账号结果回调。流式最近结果延后记录，非流式保留原逻辑；`use_count` 仍统计已建立的上游请求。回调只更新对应凭据的当前账号，不恢复状态、不清除风控标记。
4. 错误输出后不重试、不换号；终态与取消共用现有 `finally: close()`。错误详情缺失用固定说明，不落完整事件或凭据。
5. 测试复用真实 TCP Mock 与临时 SQLite，增加首事件/部分文本/工具调用后错误；单测验证 bytes 跨块、错误帧 yield 时取消及幂等关闭。环境变量在导入模块前指向临时数据目录，屏蔽代理，禁止真实上游调用。

## Risks / Trade-offs

- 错误终态使下游原先误认为成功的调用转为失败 → 这是预期修复；成功、非流式与取消路径做回归。
- 延后账号结果会遇到账号被删除或换凭据 → 回调核对账号与实际使用凭据，不写回过时对象。
- 首帧 HTTP 200 已发送 → 使用协议内错误和监控业务结果，不尝试改响应头。
- Messages 维持字节透传 → 仅旁路检测上游错误，不重组 SSE 或引入通用解析框架。

## Migration Plan

不迁移数据库、不改设置。完成本地验证和 Antigravity CLI 验收后交付差分；Git 提交、推送与 VPS 部署不属于本次任务。回退仅撤销本次网关、测试及一处 API 契约补充，保留用户 `.gitignore` 修改。
