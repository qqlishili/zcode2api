# Design: 大区优先级百位端口段与账号永久粘性架构设计（加固版）

## Context

见 `proposal.md`。网关部署于 107 VPS，通过 Mihomo 承载多出口代理，ZCode2API Python 核心负责调度 13 个上游账号。

## Goals / Non-Goals

**Goals:**
- 实现市面供给驱动的两阶段大区硬配额发牌（P0 硬分 80%+，P1 限分 20%，P2 严禁自动发牌）。
- 实现 8 个大区百位独立端口段（各留 100 端口）的物理隔离装配。
- 建立大区活跃端口动态注册表（`data/egress_registry.json`），槽位占位与在线路由物理解耦。
- 实现真机出口 IP 归属地（Ground-Truth Geo-IP）双重核验，杜绝名称正则误判。
- 实现账号地理大区离线确定性发牌与 SQLite 永久固化，杜绝运行时懒加载并发竞态。
- 实现选号器前置大区活性感知，大区故障时“选健康账号接单，绝不跨区换节点”，不浪费重试次数。
- 实现更换订阅时的跨周期节点增量合流与平滑生命周期折旧（去断崖）。
- 实现基于 Mihomo Controller REST API 的零断流平滑热重载。

**Non-Goals:**
- 不改变已有 OpenAI / Anthropic 双协议网关对外接口行为与参数。
- 不引入外部 Redis 或重型中间件，保持零外部依赖（纯 SQLite + 原生 Python）。

## Decisions

### 1. 市场供给驱动的两阶段硬配额体系（Tier-First Quota Allocation）
- **决策**：
  - **P0 核心承载区（HK / TW / JP）**：市面供给极多、网络延迟低（20~60ms）、家宽住宅资源丰富、抗阿里 WAF 表现最佳。**硬性保障分配 80%+ 账号（当前 13 个账号中锁定 10~11 个）**。
  - **P1 次级承载区（SG / US）**：市面供给充沛，但 US 延迟较高（150~220ms）。**严格限制分配不超过 20%（当前 13 个账号中限分 2~3 个）**。
  - **P2 兜底防线（KR / EU / OTHER）**：市面供给少，**严禁自动发牌新账号（配额强制为 0）**。
- **权重机制**：大区可用节点数量仅在同 Tier 内部微调权重，绝对禁止跨 Tier 倒挂（杜绝因 US 节点多而将大量账号错误发往 US）。

### 2. 百位端口段物理隔离与动态活跃注册表
- **决策**：
  - 端口段划分（各留 100 端口）：
    `HK`: `21100~21199` | `TW`: `21200~21299` | `JP`: `21300~21399` | `SG`: `21400~21499` | `US`: `21500~21599` | `KR`: `21600~21699` | `EU`: `21700~21799` | `OTHER`: `21800~21899`。
  - **动态活跃注册表（`data/egress_registry.json`）**：探活脚本在装配后实时产出当前各大区**真实监听且真机探活通过（HTTP 200）的在线端口列表**。`client_pool.py` 严格基于此动态列表进行哈希取模，绝不盲目对 100 个端口全量取模。

### 3. 槽位保留（Slot Reservation）与在线路由（Active Routing）解耦
- **决策**：
  - 节点三态机：
    - `active`：本次全量探活通过（HTTP 200），装配端口并注入 `egress_registry.json` 在线路由池。
    - `stale`：上一轮通过但本轮未响应或暂未探出。在 Mihomo 监听端口表中**保留其端口号占位 12 小时（防止端口序号漂移）**，但在 `egress_registry.json` 中**立刻剔除，绝不接收线上生产流量**！彻底杜绝黑洞流量。
    - `tombstone`：超过 12 小时或连续 3 轮失败，彻底释放端口编号。

### 4. 离线确定性发牌（Offline Seeding）与永久粘性
- **决策**：
  - 严禁在运行时业务请求链路做懒加载发牌（避免冷启动高并发抢锁与状态不一致）。
  - 上线前编写并执行确定性迁移脚本 `scripts/seed_account_regions.py`，为现有 13 个账号一次性完成大区绑定并写入 SQLite `accounts.data` JSON 的 `assigned_region` 字段。
  - 后续所有业务请求，账号专属 Client 严格且仅在该账号绑定的 `assigned_region` 活跃端口中一致性哈希轮换。

### 5. 调度器前置大区健康感知与避让容灾
- **决策**：
  - 改造 `app/store.py` 的 `select()` 选号逻辑：选号器实时感知各大区在 `egress_registry.json` 中的活跃端口数。
  - 若某大区（如 US）活跃端口数为 0，选号器在过滤候选账号阶段**直接前置跳过该大区账号**，由调度器指派拥有健康大区（如 HK）的账号接单，绝不消耗外部请求的 5 次重试预算，彻底杜绝死锁与 503。

### 6. 真机出口 IP 归属地双重校验（Ground-Truth Geo-IP）
- **决策**：
  - 节点初筛走名称正则（过滤“中转/入口/前置”等词汇）。
  - 探活阶段对上游端点发送探测的同时，校验出口 IP 的真实国家代码。若名称标为香港但出口实际为美国，强行校正归入 `US`，严防节点误分类导致跨国风控。

### 7. Mihomo Controller API 热重载
- **决策**：
  探活装配生成最新 `/etc/mihomo/config.yaml` 后，通过 `PUT /configs?force=true` 内存热加载，零中断保护 SSE 流。

## Risks / Trade-offs

- **[Risk]** 某大区活跃端口数波动频繁导致哈希打散。
  → **Mitigation**: 引入域内粘性哈希（Region-Scoped Sticky Affinity），账号在域内有优先绑定的主端口，主端口健康时始终固定，主端口下线时才在同域备用端口漂移。

## Migration Plan

1. 部署数据模型更新与离线发牌脚本（`app/models.py` + `scripts/seed_account_regions.py`）。
2. 更新网关调度感知与连接池逻辑（`app/store.py` + `app/client_pool.py`）。
3. 部署全量探活与注册表引擎（`scripts/mihomo_auto_probe.py`）。
4. 执行全量 144 节点探活，生成百位段监听与注册表，API 热重载生效。
5. 端到端实测验证。
