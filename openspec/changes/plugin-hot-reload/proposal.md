# 插件热重载 + 管理页入口（补回丢失的 R10/R11）

## 由来：这是一次「需求丢失」的补救

上一个 change（`dual-channel-plugin-upstream`）归档后，用户指出：
> **"你看下上下文，我之前提到过要热更新热重载的，为什么写方案的时候就丢失了？
> 到底是丢失多少内容了？这个我们都不知道。"**

逐条追溯（见该 change 归档目录下的 `REQUIREMENTS-TRACE.md`）确认**三项完全丢失**：

| # | 丢失的需求 | 后果 |
|---|---|---|
| **R10** | **热更新 / 热重载** | 改 `vendor/` 后必须重启整个服务 |
| **R11** | **管理页能看到并操作插件** | 只有 API，**前端零接入** → 用户"看不到" |
| **R12** | 未完成方案不归档 | 流程纪律问题，已写入追溯模板 |

**根因**（第一性原理）：`tasks.md` 的 58 项是**从"要做什么"倒推**的，
不是**从用户原话正推**的 —— 于是没被转写成 task 的需求在方案里**彻底消失**。
机制修正：**自此每个 change 必须带 `REQUIREMENTS-TRACE.md`，归档前逐行核对**。

## 本 change 要解决的四个问题

### ① 探针配对对齐生产选路（**最高优先**）

**问题**：`egress_probe` 用 round-robin 给"账号 ↔ 出口"配对，
而生产用 `resolve_proxy()` 的**一致性哈希**。两者算法不同 → **配对错位**：

```
实测 13 个账号，12 个的配对与探针不一致：
  laozuf@jkkks.com   实际 → 21200   探针测该出口用的是 kuozej@phons.online（判 ✅）
  kuozej@phons.online   实际 → 21100   探针测该出口用的是 国际-5735（判 ❌）
  ...
```

**后果**：**出口门禁基于错误数据** —— 探针说"某出口不可用"（基于账号 A），
但真正会走该出口的是账号 B，B 可能完全正常。反之亦可能漏判。

**修法**：探针改用 `resolve_proxy(account)` 取"该账号**真正会走**的出口"，
使探测配对与生产一致。

### ② 管理页 UI（插件状态 + 同步 + 重载）

**问题**：`GET/POST /admin/api/plugin-auth/{status,sync}` 已实现，但
`frontend/` **零接入** —— `grep "plugin|vendor" frontend/` 为空。

**修法**：在管理页加一块「插件通道」面板：
- 显示 `stale`（是否需要同步）、宿主是否存活、当前/已加载指纹
- 显示 vendor 版本状态（`vendor_status`：插件 commit、host.js sha256 差异）
- **「同步账号凭证」按钮**（调已有的 sync API）
- **「重载插件」按钮**（本 change 新增的接口，见 ③）

### ③ 插件代码热重载（不重启服务）

**问题**：当前改 `vendor/magpie_host.js` 或 `vendor/magpie-plugins/` 后，
**必须 `systemctl restart zcode2api`** 才生效（宿主是服务进程的子进程）。

**为什么"重启服务"不可接受**：重启会中断所有在飞请求、清空断路器与
验证码水库（内存态）、重跑启动流程。

**修法（待设计）**：新增 `POST /admin/api/plugin/reload`：
- 复用已有的 `stop_plugin_host(drain=True)` + `start_plugin_host()`（**不重启服务**）
- 重载前可选：`git -C vendor/magpie-plugins fetch && reset --hard`（拉最新）
- 失败回滚：与 `vendor_check.apply_plugin_update()` 同一策略

**注意**：这与「账号凭证同步」是**两件事**：
| | 触发原因 | 影响 |
|---|---|---|
| 账号凭证同步 | 账号增删改 | 重建 `plugin-auth.json` |
| **插件代码重载** | **vendor 文件变化** | **重新加载 index.mjs / host.js** |

两者都要重启宿主，但**语义不同**，UI 上应分开呈现。

### ④ reqlog 分离「客户端断开」与「上游失败」

**问题**：`reqlog` 把两者都记成 `status=499`，无法区分。

**实测**：`evidence.db` 里 68 个 499 **全部**来自测试脚本
`resp.read(1)`（只读首字节就关闭连接）—— 已用 A/B 实验证明
（只读 1 字节 × 3 → 新增 3 个 499；读完整 × 3 → 新增 0 个）。

**后果**：统计上看起来"49% 请求失败"，实际是单一测试客户端的产物。

**修法**：`reqlog` 增加独立的 `client_abort` 标记（或 `status=None` + `reason="client_abort"`），
让"客户端主动断开"与"上游/服务端失败"在统计上可分离。
