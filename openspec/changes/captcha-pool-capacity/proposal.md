# 验证码预解池的容量上限与命中率

## 现象（2026-10-15 实测）

按 `pin-captcha-egress-and-refill-domain` 的 8.1 要求跑端到端验收，命中率随
**请求间隔**剧烈变化：

| 请求间隔 | 命中率 | `t_first` p95 | 判定（要求 ≥80% / ≤5 s） |
|---|---|---|---|
| **0.4 s**（压测） | **65%**（13/20） | **19919 ms** | ❌ |
| **12 s**（真实用户） | 约 87.5%（7/8） | 见下方正式重测 | 待定 |

分布呈**双峰**：
- 快组 ~1.1–2.6 s → 水库命中（`captcha {"source":"hit"}`）
- 慢组 ~13–20 s → 现场求解（`captcha {"source":"foreground"}`，
  单次 `solve_ms` ≈ 6.5–7.7 s + `queue_wait_ms` ≈ 5–6 s）

## 根因（三个因素叠加，均可复查）

**① 求解并发被钳制为 1**

```python
# app/captcha.py:209-212
cores = os.cpu_count() or 1
concurrency = 1 if cores <= 1 else max(1, cores - 1)
self._cpu_semaphore = asyncio.Semaphore(concurrency)
```

VPS 实测 **2 核**，且**负载持续 2.09 / 1.90 / 1.83（已满载）** → 求解**串行**。
单次 ≈ 7 s → **稳态补给速率 = 1 枚 / 约 7 s**。

**② 目标库存只有 1 枚**

```python
# app/settings.py:68
CAPTCHA_REGIONAL_POOL_MIN = _int("CAPTCHA_REGIONAL_POOL_MIN", 1)   # 每端口目标库存
```

补充门槛是 `< MIN` 才补（`captcha.py:367`），且轮询间隔 3 s →
token 被用掉后有一段空窗。

**③ 后台补货"让路"过于激进**

```python
# app/captcha.py:522（以及 633 的同类判断）
if background and (self._foreground_demand or self._cpu_semaphore.locked()):
    return None        # 后台补货直接放弃
```

只要有任何前台请求在等、或求解槽被占，**后台补货就跳过** →
有流量时预热几乎不生效，池长期停在 0–1 枚。

**合成效果**：请求间隔 < 7 s 时补给跟不上消耗，必然大量现解。

## ⚠️ 不能简单提高 MIN（负收益）

当前只有 3 个可服务端口（`serviceable_ports`），若把 MIN 提到 3：

```
3 端口 × 3 枚 = 9 枚预解
串行求解 ≈ 7 s/枚 → 补满需约 63 s
而 CAPTCHA_TOKEN_TTL = 75000 ms（75 s）→ 补满即过期
且预解会与正常请求争抢唯一的 CPU 求解槽
```

即：**在单核求解的现实下，提高库存只会让"过期前的无效预解"变多。**

## 待回答的问题

1. **容量的真实上限是多少？** 在当前硬件（2 核、已满载）下，
   可持续支撑的最大请求速率（请求/秒）是多少？命中率曲线如何？
2. **能否提高求解并发？** 求解是 Node 子进程（`captcha_node/solver.js`）+ 浏览器环境，
   主要开销是 CPU 还是等待？若是等待，并发可 >1；若是 CPU，则需要更多核。
3. **能否让后台补货更聪明？** 例如：留出固定比例的求解槽给后台、
   或在前台空闲的间隙补货 —— 而不是"有前台就完全放弃"。
4. **验收线是否该按容量重新定义？** 若容量上限就是约 1 请求 / 7 s，
   那么"p95 ≤ 5 s"在超过该速率时**物理上不可能达成**，
   8.1 的验收条件需要相应改为"在容量内的请求速率下"。

## 范围

**调查 + 提出修复方案**。修复本身（改并发策略 / 补货策略 / 硬件升配）
需要单独评估后另开 change，因为它触及请求路径的延迟特性。

## 补充实测：冷启动 vs 稳态（2026-10-15）

同一套间隔（12 s）跑两轮，结论完全不同：

| 轮次 | 前几个请求 | 其后 | p95 | 判定 |
|---|---|---|---|---|
| **未预热**（池是空的） | 第 1–3 个 7.7–7.8 s | 第 4–20 个全 < 3 s | **7787 ms** | ❌ |
| **预热 3 个后统计** | — | — | 见 `pin-captcha` 8.1 最终记录 | — |

**未预热那轮的完整分布**：

```
最小 8 个: 1077 1148 1160 1174 1211 1214 1231 1242 ms
最大 3 个: 2927 7728 7790 ms
中位:      1254 ms
成功率:    20/20
499/503:   0
```

**只有第 2、3 个请求超标**（第 1 个 2023 ms 反而正常），其后 18 个全部 < 3 s。

**含义**：冷启动（池为空）时，头两个请求要现解；一旦池被填起来，
稳态命中率约 90%（18/20），**p95 被冷启动的头两个拉高**。

**对验收线的启示**：「`t_first` p95 ≤ 5 s」这个条件在**包含冷启动的样本**里
会被少数首批请求主导。合理的验收应区分：
- **冷启动指标**：首个请求的延迟上界（当前约 10 s）
- **稳态指标**：预热后的 p95（当前约 3 s，达标）

**这不是产品缺陷，是验收样本的构成问题** —— 但需要有意识地定义，
否则同一套代码会因"跑之前池是空是满"得出相反的验收结论。
